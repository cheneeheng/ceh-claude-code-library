# ceh-codebase-explanation

Leave a codebase understood: the passes an agent runs to explain code it did not write, to a person
in the session or into a file that outlives it. Split out of `ceh-coding-conduct`, which keeps the
rules for how an agent behaves while it codes.

## Skills

| Skill                      | When it loads                                                                                            | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `explain-until-understood` | On demand — when someone in the session needs a subsystem, design, diff, or unfamiliar tool explained    | How an explanation is built and what to do when it misses: assume the reader is new to the project and knows nothing about the subject, and say what floor you are building from; read the real code (never a design doc), foundations before the specific case, plain language (concept before name, every term of art defined at first use, project-local names included), verified output over described output, plain-ASCII pictures for structure and time (no box-drawing or arrow glyphs), a numbered walk of one ordinary case end to end, close on a transferable rule plus a self-test. Ships the escalation ladder — prose → steps → pictures → foundations — with the rule that a miss at pictures means a skipped foundation, not a missing detail; a reader lost on a _word_ is not on the ladder at all. Writes no files by default — `.agents_workspace/` scratch notes on request, an opt-in learning workspace (`.agents_workspace/product/learning/<subject>.md`: terms the reader has said back, rules, self-test history, what comes next) that a later session opens with two self-test questions, and one narrow repo path for a subsystem explainer no other skill owns. |
| `explain-codebase`         | On demand — when the ask is to understand a whole repo and leave the understanding in a file             | Whole-repo orientation, for code repos and Markdown or text knowledge bases alike: what each component (or topic area) does, how they connect, and the key flows, written into a git-ignored `.agents_workspace/CODEBASE_EXPLAINED.md`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `document-architecture`    | On demand — when the system's shape or a durable decision needs recording                                | The living `.agents_workspace/product/ARCHITECTURE.yaml`, with its Markdown rendered beside it (an old `.agents_workspace/ARCHITECTURE.md` is moved there on first run): a 3-second Overview, Mermaid diagrams (components, key flows, data model, state machines), and an append-only Key Decisions log. Updated on shape change, not every commit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `trace-code-rationale`     | On demand — when the question is why code is the way it is, or before removing code that looks pointless | Traces the target through `git log -L`, blame, pickaxe, and the linked PRs and issues, and answers in chat with every claim cited to a commit, PR, or issue, stated reasons kept apart from inferred ones, and a Not recorded list where the history is silent. Read only. Needs `git`, and `gh` for the PR lookup.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `maintain-glossary`        | On demand — when a term is used two ways, two words name one thing, or a new concept needs a name        | Greps each term's real usages in code and prose, settles one word and one domain-language definition (asking the user when the choice changes meaning), writes it to a committed `GLOSSARY.yaml` (`glossary/v2`, checked by a model) with `GLOSSARY.md` rendered beside it, converting an old Markdown-only glossary without losing an entry, and lists files still using a rejected alias without renaming anything. Works for code repos and knowledge bases. It's working if each entry has an _Avoid:_ list and the reply names the stragglers as `path:line`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

**Manual triggers**

- `explain-until-understood` — `/explain-until-understood [what to explain]`, or ask for something to be explained until it makes sense.
- `explain-codebase` — `/explain-codebase`, or say `"explain this codebase"` / `"what does this repo do"`.
- `document-architecture` — `/document-architecture`, or say `"write the architecture doc"` / `"diagram the system"` / `"record this decision"`.
- `trace-code-rationale` — `/trace-code-rationale <file>[:<lines>]`, or ask `"why is it like this"` / `"why was this added"` / `"is this safe to remove"`.
- `maintain-glossary` — `/maintain-glossary [term ...]`, or ask `"what do we call X"` / `"define our terms"`.

## Hooks

| Hook                                                                          | Event                                        | Script                    | Default |
| ----------------------------------------------------------------------------- | -------------------------------------------- | ------------------------- | ------- |
| [Architecture render](#architecture-render-and-generated-markdown-guard)      | `PostToolUse` (`Edit`, `Write`, `MultiEdit`) | `artifact-render-hook.py` | on      |
| [Generated Markdown guard](#architecture-render-and-generated-markdown-guard) | `PreToolUse` (`Edit`, `Write`, `MultiEdit`)  | `generated-md-guard.py`   | on      |

### Architecture render and generated Markdown guard

`document-architecture` saves `.agents_workspace/product/ARCHITECTURE.yaml` (`architecture/v3`).
After every write to it, the render hook checks the YAML against its model through `uv` and renders
the `ARCHITECTURE.md` beside it with its section numbers and Contents list, or reports each error back
to the agent and leaves the Markdown as it was. `maintain-glossary` saves `GLOSSARY.yaml`
(`glossary/v2`), and the same hook checks it and renders `GLOSSARY.md`. A `GLOSSARY.yaml` with no
schema key is reported only at the session's root or in `docs/` beside a `GLOSSARY.md`, so a
project's unrelated `GLOSSARY.yaml` is left alone. The guard denies a direct edit to a generated
Markdown file and names its YAML. Both need `uv`: without it the agent is told once per session
that the file went unchecked. `CEH_ARTIFACT_CHECK=off`, or `CEH_DISABLED_HOOKS` with
`artifact-render-hook` or `generated-md-guard`, switches them off.

## Where its files live

Since 2026-11-14 this plugin saves and reads product files in `.agents_workspace/product/`. A project with a root `product/` moves each file to the same sub-path there, or names its location in `CLAUDE.md`.
